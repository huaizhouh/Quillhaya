# issue1014：续写提示、反馈分类与退出保存恢复

日期：2026-10-16。对应 [issue1014.md](../issues/issue1014.md) 的三项问题。继续使用 Electron、React、TypeScript、Zod、CodeMirror 6 和 Node fetch；没有新增依赖。前次要求隐藏的上下文明细继续不出现在界面中。

## 1. 顺序续写不提示前句上下文变化

**根因**：原逻辑比较请求时和当前的完整上下文签名。一句审议时还没有后文，写完下一句后，`after: []` 变成 `after: [下一句]`，于是把正常续写也标成“上下文已变化”。正在分析中的前句返回时也会出现同样提示。

现在把“请求与缓存使用哪些上下文”和“是否提醒旧结果过期”分开：

- 自动请求、手动重评、缓存键仍包含最多两句完整前文和一句完整后文。
- 提示判断使用该结果实际的 `contextSnapshot`；前文仍正常比较。
- 原审议没有后文时，新出现的后文不触发提示。该后文在用户主动重评之前不属于这份旧结果的审议依据，因此不会因其变化而提示旧结果过期。
- 原审议已使用后文时，修改或删除该后文仍提示；撤销回原上下文会清除提示。
- 正常续写不重跑已审议的前句，也不取消其在途请求。手动重评仍读取最新前后文。

实现：[`contextChanged()` / AnalysisCoordinator](../src/core/coordinator.ts)。这只是界面提示规则调整，不会伪造上下文已发送，也不把新后文写进旧结果快照。

## 2. 客观错误和可选优化同时保留

### 提示词调整

上一轮强调客观错误优先，但“只建议必要修改”和以语法为中心的复核容易让模型忽略优化，或为了满足要求把风格偏好升级成语法错误。

现在系统提示词及最多一次独立复核明确区分：

| 情况 | 期望输出 |
| --- | --- |
| 违反具体规则且需要实际修正 | `error`，解释错误依据 |
| 语法正确，但自然度、简洁度、清晰度或语气有明确改善空间 | 对应非语法类型的 `improvement` |
| 同时存在真实错误和有效优化 | 两类均可保留，真实错误在前，总数仍最多三项 |
| 正确且自然，没有值得提出的优化 | `good` |

根据后续反馈，删除针对示例词句追加的特殊规定，将分类依据收敛为上表中的通用原则。格式示例涵盖 good、客观错误、可选优化和混合结果；推荐句与问题列表对应，并保留原意。

独立复核仍从原文、相同上下文和待核验修改（原文片段、候选替换）重新分析，不附第一轮 assistant 的分类和解释。复核目标同时包含准确性与表达质量，明确要求不要因为没有发现语法错误就删掉有价值的优化。没有增加复核轮数：含 improvement 的单句结果最多一轮，good/纯客观错误/全文不因此额外复核。

### 结果校验

已撤回本轮新增的逐条比较原文片段与建议片段是否相同的拦截，也删除对应的提示语和测试断言。保留已有字段、类型、中文说明及原文引用等协议校验；语言判断由模型结合上下文完成，不根据个别误判不断扩充程序中的语言规则。

grammar/spelling 与 improvement 冲突时，修复提示明确要求先核验分类：真正错误才用 error；风格建议应调整 type 并保留 improvement，不能机械升级 severity。有效结果仍按真实错误优先排序，没有在程序中批量把优化升级为错误，也没有删除全部优化的兜底逻辑。

### 保留复核实际采用的优化

真实 gemma4:e2b-mlx 回归发现，即使提示词明确要求保留，复核也可能在最终推荐句中删除冗余，却从 issues 漏掉对应优化。因此增加 `retainAppliedImprovements()`：保存首轮合法的 improvement 候选；如果最终 issues 无法完整解释推荐句，尝试补回已采用的候选。

补回条件是严格的字面重建：每条原文片段必须唯一且互不重叠，把最终 issues 和候选修改应用到原句后，必须得到最终推荐句（只规范空白及标点前多余空格）。未采用的建议、与最终语法修正冲突的建议、重复原文片段都不补回；总数仍最多三条。该逻辑只补充模型已经实施的改写说明，不改变最终推荐句，也不产生新的语言建议或网络调用。

单元测试覆盖实际采用的删除优化可保留、未采用不补回、重复片段不猜测；已有 trouble → affects 被纠正为 trouble → troubles 的测试继续确保旧风格建议不会覆盖新语法判断。

实现：[`systemPrompt()`、`parseResult()`、`retainAppliedImprovements()`、CompatibleProvider](../electron/llm/provider.ts)。结构校验不能保证每条中文解释或语言判断正确；实测结果见下方验证记录。

## 3. 退出时保存后恢复为真实文件

**根因**：保存 IPC 成功后，renderer 调用了 `setDoc()`，但 React 更新是异步的。`canLeave()` 随即继续调用关闭接口，把尚未更新的 `docRef.current`（旧文件名、dirty=true）传给主进程。关闭流程再次保存草稿，覆盖了保存成功时的正确文档元数据。

真实文件路径其实仍留在主进程/草稿中，因此出现“界面显示未命名、再次退出仍询问保存，但保存却不再选择路径”的不一致。

现在做两层修复：

1. **renderer 同步快照**：保存成功后先同步更新 `docRef.current` 的文件名、hasFile 和 dirty，再更新 React 显示；紧接着的关闭流程立即能拿到保存后的状态。如果保存期间继续输入，仍按保存时的正文快照判断，新输入保持 dirty。
2. **主进程校正元数据**：`Documents.fileState()` 根据真实关联路径生成文件名/hasFile，根据当前正文与已保存版本比较 dirty。写草稿和恢复草稿统一使用它；旧 renderer 快照不能把正确文件名、已保存状态覆盖回去。

比较文本时仅去除已保存文件的 BOM，并把 CRLF/CR 规范为编辑器使用的 LF；不 trim 正文，空格和真实新输入仍算改动。保存文件的编码/换行风格维持原机制。

**已有异常草稿也兼容**：只要草稿中已有正确路径和 savedText，下次恢复会得到真实文件名与正确 dirty。没有文件关联的草稿仍显示未保存。恢复不覆盖磁盘文件；外部文件改动仍由原有保存冲突检测处理。

实现：[`App.tsx` 的 saved()](../src/App.tsx)、[`documents.ts` 的 fileState()/restore()/draft()](../electron/storage/documents.ts)。

1. 顺序完成下一句不提示前句；手动重评已包含后文后，修改该后文仍有提示。
